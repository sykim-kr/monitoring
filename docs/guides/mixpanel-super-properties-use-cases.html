Mixpanel Implementation Guide

Super Properties
실무 Use Case

Super Property는 한 번 등록하면 해당 기기에 저장되고, 이후 전송되는 이벤트에 자동으로 붙는 공통 이벤트 속성입니다. 반복적으로 전달해야 하는 사용자·세션·환경 맥락을 일관되게 수집하여, 이벤트 추적 코드를 단순화하고 분석의 분해 축을 풍부하게 만듭니다.

AcquisitionExperimentPlatform Session ContextLifecycleQA
좋은 후보여러 이벤트에서 반복되고 일정 기간 유지되는 값
피해야 할 후보이벤트 순간마다 바뀌는 거래·상품·행동 값
핵심 주의점기기 로컬 저장값이므로 서버 이벤트에는 자동 전파되지 않음

1. 개념과 데이터 모델

한 줄 정의: Super Property는 클라이언트 SDK가 기기에 보존하고 이후 이벤트마다 자동 첨부하는 글로벌 Event Property입니다.
구분무엇을 표현하는가적합한 예시분석 시점
Event Property그 행동이 일어난 순간의 구체적 맥락product_id, price, coupon_used, search_term해당 이벤트에 기록된 과거 값
Super Property여러 후속 이벤트에 공통 적용할 지속적 맥락platform, app_version, experiment_variant, acquisition_channel각 이벤트 발생 당시 자동 첨부된 값
User Profile Property사용자의 현재 상태와 속성plan, industry, current_ltv, preferred_language프로필의 현재값과 이벤트를 조인
중요: Super Property와 User Profile Property는 같은 것이 아닙니다. 예를 들어 사용자의 요금제가 바뀌었을 때, 과거 이벤트를 당시 요금제 기준으로 보고 싶다면 이벤트에 값이 남아야 합니다. 현재 요금제만 보고 싶다면 User Profile이 적합합니다. 분석 목적에 따라 양쪽에 함께 저장할 수도 있습니다.

2. 대표 Use Case 10가지

01 Acquisition

최초 유입 출처 유지

first_utm_source, first_utm_campaign, initial_referrer를 최초 1회 등록합니다.

  • 유입 채널별 활성화·전환·리텐션 비교
  • register_once로 최초 획득값 보호
  • 모바일은 딥링크 값을 직접 파싱해야 할 수 있음
02 Campaign

현재 캠페인 터치 맥락

현재 방문 또는 앱 오픈을 만든 utm_source, utm_medium, utm_campaign을 일정 기간 후속 이벤트에 붙입니다.

  • 광고 클릭 이후의 실제 제품 행동 추적
  • 새 캠페인 유입 시 값을 갱신
  • First-touch와 Current-touch를 분리 명명
03 Experiment

A/B 테스트 실험군

experiment_id와 variant를 노출 시점에 등록해 후속 이벤트 성과를 실험군별로 비교합니다.

  • 전환뿐 아니라 리텐션·다운스트림 영향 분석
  • 실험 종료 또는 재할당 시 해제·갱신
  • 동시 실험은 개별 속성 또는 노출 이벤트 병행
04 Environment

플랫폼·앱 버전·배포 채널

platform, app_version, build_number, release_channel을 공통 첨부합니다.

  • 릴리즈 전후 핵심 퍼널 변화 확인
  • 특정 버전의 오류·이탈 집중 탐색
  • 웹·앱 통합 프로젝트에서 플랫폼 비교
05 Localization

언어·국가·서비스 리전

language, country, service_region, timezone 같은 환경 맥락을 유지합니다.

  • 국가별 온보딩 성과와 기능 채택률 비교
  • 언어 변경 시 즉시 갱신
  • 민감한 정밀 위치 대신 분석 목적의 범주형 값 사용
06 Account Context

현재 워크스페이스·계정 맥락

B2B SaaS에서 workspace_id, account_tier, member_role을 현재 작업 컨텍스트로 등록합니다.

  • 워크스페이스 전환 시 반드시 덮어쓰기
  • Group Analytics와 함께 사용 가능
  • 권한별 기능 사용과 전환 차이 파악
07 Journey

온보딩·라이프사이클 단계

journey_stage 또는 onboarding_state를 상태 변경 시 갱신합니다.

  • 각 단계에서 자주 발생하는 행동 비교
  • 단계별 이탈 신호와 활성화 행동 탐색
  • 상태 전환 이벤트도 별도로 추적 권장
08 Session

세션 시작 맥락

session_entry_page, session_type, login_state_at_start를 세션 시작 시 등록합니다.

  • 세션의 진입 맥락이 후속 행동에 미친 영향 분석
  • 세션 종료·새 세션 시작 시 재설정
  • 세션 ID는 고카디널리티이므로 목적을 명확히 함
09 Feature Configuration

기능 설정·권한 상태

notifications_enabled, personalization_enabled, permission_level 등을 변경 시 갱신합니다.

  • 설정 상태별 리텐션·기능 사용 비교
  • 분석에 필요한 핵심 설정만 선별
  • 이벤트 순간의 상태를 보존해야 할 때 유용
10 QA & Operations

내부 사용자·테스트·데이터 출처

is_internal_user, environment, tracking_source, debug_mode를 공통 첨부합니다.

  • 운영 리포트에서 사내·테스트 트래픽 제외
  • 클라이언트와 서버 데이터 품질 비교
  • 개인 이메일 대신 Boolean 또는 역할 범주 사용

3. 무엇을 Super Property로 만들 것인가?

Super Property

여러 이벤트에서 반복되고, 일정 기간 유지되며, 이벤트 발생 당시의 값이 분석에 필요할 때.

일반 Event Property

가격, 상품, 쿠폰, 검색어처럼 이벤트마다 달라지는 순간적 맥락일 때.

User Profile

현재 플랜, 누적 LTV, 현재 등급처럼 사용자의 최신 상태를 조회하려는 목적일 때.

판단 질문Yes라면
이 값이 여러 종류의 이벤트에 반복해서 필요한가?Super Property 후보
값이 한 행동마다 달라지는가?일반 Event Property
과거 이벤트를 당시 값으로 분석해야 하는가?Event/Super Property에 기록
사용자의 최신값만 중요하며 과거 이벤트까지 소급 적용해 보고 싶은가?User Profile Property
로그아웃·워크스페이스 전환 후 값이 남으면 오염되는가?명시적 unset/reset 설계 필수

4. JavaScript 구현 패턴

4.1 지속되는 공통 속성 등록

mixpanel.register({
  platform: 'web',
  app_version: '2026.08.1',
  language: 'ko-KR'
});

// 이후 이벤트에 위 속성이 자동 첨부됩니다.
mixpanel.track('feature_used', {
  feature_name: 'retention_report'
});

4.2 최초 유입값 한 번만 보존

mixpanel.register_once({
  first_utm_source: getParam('utm_source') || 'direct',
  first_utm_campaign: getParam('utm_campaign') || '(none)',
  first_landing_page: window.location.pathname
});

4.3 상태 변경 시 갱신

function updateJourneyStage(stage) {
  mixpanel.register({ journey_stage: stage });
  mixpanel.track('journey_stage_changed', { stage });
}

updateJourneyStage('activated');

4.4 실험 종료·컨텍스트 종료 시 제거

mixpanel.unregister('experiment_variant');
mixpanel.unregister('workspace_id');

4.5 로그아웃 시 사용자 상태 정리

mixpanel.track('logout');

// 프로젝트의 익명 사용자 정책에 맞게 사용합니다.
mixpanel.reset();
구현 원칙: Super Property는 이벤트 전송 전에 등록해야 합니다. 해당 값이 바뀌는 순간에는 등록값을 갱신하고, 더 이상 유효하지 않은 컨텍스트는 제거해야 다음 사용자의 이벤트나 다른 워크스페이스 이벤트를 오염시키지 않습니다.

5. 설계·운영 체크리스트

  • 현재값과 당시값을 구분: User Profile과 Event/Super Property의 분석 목적을 먼저 정의합니다.
  • First-touch와 Current-touch를 구분: 예: first_utm_source와 utm_source.
  • 변경 트리거 정의: 로그인, 언어 변경, 워크스페이스 전환, 실험 노출, 앱 업데이트 시점을 명시합니다.
  • 해제 조건 정의: 로그아웃, 실험 종료, 세션 종료, 계정 전환 시 unset/reset 여부를 설계합니다.
  • 클라이언트·서버 일관성 확인: 클라이언트에 저장된 Super Property는 서버 이벤트에 저절로 붙지 않으므로 서버에도 동일 속성을 전달하거나 데이터 모델을 별도로 설계합니다.
  • 카디널리티 관리: URL 전체값, 자유 입력 텍스트, 임의 ID를 무분별하게 공통 속성으로 만들지 않습니다.
  • 개인정보 최소화: 이메일·전화번호·정밀 위치 대신 분석 목적에 맞는 범주형 또는 비식별 값을 사용합니다.
  • 검증 이벤트 준비: QA 환경에서 실제 이벤트 payload에 속성이 정확히 붙는지 확인합니다.
